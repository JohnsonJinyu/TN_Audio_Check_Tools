# 数据提取系统架构说明

> **版本**: 1.0  
> **更新日期**: 2026-05-25  
> **适用范围**: TN_Audio Tools — 测试数据提取子系统  
> **目的**: 完整记录数据提取管道的工作逻辑、扩展点和新增工作模式的标准化流程

---

## 1. 系统概览

数据提取子系统负责从ACQUA 6.0音频测试报告（.xlsx/.doc/.docx）中自动提取测试数据，并回填到Voice Tuning Checklist中。系统支持多种终端工作模式（Handset/Handsfree/Headset/Electrical Interface），每种模式有独立的提取规则配置。

```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│  规则配置     │    │  测试报告     │    │  Checklist   │
│  (JSON5)     │    │  (.xlsx/doc) │    │  (.xlsx)     │
└──────┬───────┘    └──────┬───────┘    └──────┬───────┘
       │                   │                   │
       ▼                   ▼                   ▼
┌──────────────────────────────────────────────────────┐
│               6层数据提取管道                          │
│                                                      │
│  [1] 规则加载 → [2] 报告解析 → [3] 模式选择          │
│       ↓              ↓              ↓                │
│  [4] 逐项提取 → [5] 结果汇总 → [6] 回写Excel         │
└──────────────────────────────────────────────────────┘
```

## 2. 核心数据流（6层管道）

### 2.1 第1层：规则加载 (reportSource.js)

**入口**: `processReports()` → `loadRules(rulePath)`

**流程**:
1. 读取 `moto_rules_for_analysis.json5`（规则束入口）
2. 用JSON5解析器解析（支持注释、尾随逗号）
3. `normalizeRulesConfig()` 递归加载所有profile对应的规则文件
4. 返回标准化规则对象：
   ```js
   {
     ruleBaseInfo: { ... },
     defaultProfileKey: "handset",
     ruleProfiles: {
       handset: { ruleBaseInfo, globalMatchConfig, extractItemList: [...] },
       handsfree: { ... },
       headset: { ... },
       electrical_interface: { ... }  // 新增模式
     }
   }
   ```

**关键文件**:
- `src/main/services/testDataExtraction/reportSource.js` — `loadRules()`, `normalizeRulesConfig()`
- `src/main/services/testDataExtraction/index.js` — `resolveBundledRulesPath()`

---

### 2.2 第2层：报告解析 (reportSource.js + xlsxReportSource.js)

**入口**: `parseReport(reportPath)`

**分发逻辑**:
| 扩展名 | 解析器 | 数据源 |
|--------|--------|--------|
| `.xlsx` / `.xls` | `parseXlsxReport()` | Detailed + Values 工作表 |
| `.doc` / `.docx` | `parseDocxReport()` | 文本 + 结构化段落/表格 |

**xlsx解析详情** (`xlsxReportSource.js`):
1. `readDetailedRows()`: 读取Detailed工作表 → 14列标准行数据
2. `buildDetailedRowContexts()`: 构建每行的搜索文本（SMD + Name + Description + Direction + ...）
3. `buildValuesDerivedRows()`: 从Values工作表构建2D矩阵行
4. 自动推断 `reportContext`:
   - `measurementObject`: 主导Measurement Object
   - `bandwidth`: NB / WB / SWB
   - `network`: VoLTE / VoWiFi / VoNR / WCDMA / GSM
   - `codec`: EVS / AMR
   - `terminalMode`: HA / HE / HH / HF / HS → **需扩展EI**

**Detailed行标准列** (14列):
```
SMD | Name | ResultName | Value | Status | Unit | Description | Comment |
Direction | VolumeCTRL | Bandwidth | BGNScenario | RequirementType | UseCase | Measurement Object
```

---

### 2.3 第3层：模式选择 (reportExtractor.js)

**入口**: `processSingleReport()` → `resolveRulesForReport()`

**模式选择链**:
```
terminalMode (来自报告/UI)
  → resolveTerminalModeKey() → profileKey
  → resolveRuleProfileKey() → 从rules.ruleProfiles选择对应规则
```

**当前映射表**:
| terminalMode | profileKey | 规则文件 | checklist工作表 |
|-------------|------------|---------|----------------|
| HA | handset | moto_rules_handset.json5 | Handset |
| HH, HF | handsfree | moto_rules_handsfree.json5 | Handsfree |
| HE, HS | headset | moto_rules_headset.json5 | Headset |
| **EI** | **electrical_interface** | **moto_rules_electrical_interface.json5** | **ElectricalInterface-Analogue** |

**关键函数**:
- `resolveTerminalModeFromInterface(value)`: UI选项 → terminalMode
- `resolveTerminalModeKey(value)`: terminalMode → profileKey
- `resolveChecklistModeKeyFromName(path)`: checklist文件名 → profileKey
- `resolveRuleProfileKey(reportData, checklistPath)`: 综合决策
- `findModeChecklistTemplate()`: 自动查找对应模式的checklist模板
- `resolveChecklistPathForReport()`: 推导正确的checklist路径

**适用性判断** (`isItemApplicable()`):
每条提取规则支持按5个维度过滤：
- `applicableTerminalModes` / `excludedTerminalModes`: 终端模式
- `applicableBandwidths` / `excludedBandwidths`: 带宽（NB/WB/SWB）
- `applicableNetworks` / `excludedNetworks`: 网络类型
- `applicableVocoders` / `excludedVocoders`: 编码器
- `applicableCustomers` / `excludedCustomers`: 客户

---

### 2.4 第4层：逐项提取 (reportAnalysis.js)

**入口**: `processSingleReport()` 循环 `extractItemList`

**6种提取类型**:

| 类型 | 源 | 算法 | 适用场景 |
|------|---|---|---------|
| `summary_table_match` | Status Overview汇总表 | 关键词+suffix匹配SMD行，取Single Value | 响度、噪声、频响等汇总值 |
| `formula_calc` | 汇总表 | `standardValue - baseItem.marginValue` | 单频干扰余量计算 |
| `detail_anchor_extract` | 详情段落 | 搜索anchor文本，正则提取数值 | 发送频响最小距离 |
| `table_struct_extract` | 报告表格 | 表头+行名匹配→交叉单元格 | 回声延迟、ECC分类 |
| `regex_extract` | 任意文本 | 直接应用matchRegex提取$1 | 结构化字段 |
| `status_judge` | 结论区 | 提取"OK"/"Not OK" | 失真判定 |

**文本归一化** (`normalizeText()`):
1. 去行首数字序号（`9.2.1` → 空）
2. 多空格→单空格
3. 大小写不敏感
4. 去行尾OK/Not OK等符号
5. 特殊替换：`HANB/HAWB/HASB` → `HABAND`（统一band token）

**关键词匹配** (`hasAllKeywords()`):
- 模糊匹配（fuzzy）：所有coreKeywords必须出现在归一化文本中
- 精准匹配（exact）：归一化后完全一致
- 降级匹配：fallbackKeywords → 去可选词 → 最低3个核心词

**Suffix机制**:
- `requiredSuffix`: 必须后缀（如MAX、NOM、MIN），用于区分同关键词不同音量
- `forbiddenSuffix`: 禁止后缀（如ECRP、20UP），用于排除不相关变体
- 全局黑名单：`#1`~`#10`、`1o2`、`2o2`

### 2.6 第6层：回写Excel (checklistWriter.js)

**入口**: `applyResultsToChecklist()`

**流程**:
1. 打开checklist模板xlsx

4. 保存到输出路径

## 3. 规则文件JSON5结构规范

### 3.1 规则束入口 (moto_rules_for_analysis.json5)

```json5
{
  "ruleBaseInfo": {
    "ruleName": "规则名称",
    "version": "2.0",
    "updateTime": "2026-03-17",
    "fitReportType": "适配的报告类型",
    "fitChecklist": "适配的checklist说明"
  },
  "defaultProfileKey": "handset",  // 默认模式
  "ruleProfiles": {
    "profileKey": {
      "label": "显示名称",
      "terminalModes": ["HA"],     // 对应的终端模式标识
      "rulePath": "./moto_rules_xxx.json5"  // 相对路径
    }
  }
}
```

### 3.2 单模式规则文件 (moto_rules_xxx.json5)

```json5
{
  "ruleBaseInfo": { /* 版本+适用范围 */ },
  
  "globalMatchConfig": {
    "textNormalize": {
      "removeNumberPrefix": true,    // 去行首序号
      "multiSpaceToSingle": true,    // 多空格→单空格
      "caseInsensitive": true,       // 大小写不敏感
      "trimSpecialChar": true        // 去行尾符号
    },
    "defaultMatchMode": "fuzzy",     // fuzzy | exact
    "globalForbiddenSuffix": ["#1","#2",...],
    "globalRequiredSuffix": ["MAX","MIN","NOM","AVERAGE","AVG"]
  },
  
  "extractTemplate": { /* 6种提取类型定义（固定不变） */ },
  
  "extractItemList": [
    {
      "itemId": 1,                    // 唯一编号
      "checklistDesc": "描述文本",    // 仅用于阅读
      "outputCell": "I6",            // checklist目标单元格
      "extractType": "summary_table_match",  // 提取类型
      "coreKeywords": ["关键词1","关键词2"],  // 必须全部包含
      "fallbackKeywords": ["降级关键词"],     // 可选降级匹配
      "forbiddenSuffix": ["排除后缀"],        // 覆盖全局黑名单
      "requiredSuffix": ["必须后缀"],         // 覆盖全局白名单
      
      // 仅 formula_calc 类型：
      "formula": {
        "standardValue": -74,
        "baseItemId": 11,
        "targetField": "marginValue"
      },
      
      // 仅 detail_anchor_extract 类型：
      "anchorConfig": {
        "anchorText": "锚点文本",
        "valueMatchRule": "提取规则描述",
        "valueRange": [0, 20]
      },
      
      // 仅 table_struct_extract 类型：
      "tableConfig": {
        "tableHeaderKeywords": ["表头关键词"],
        "rowKeywords": ["行关键词"],
        "targetColumnName": "目标列名"
      },
      
      // 仅 regex_extract 类型：
      "matchRegex": "正则表达式",
      
      // 适用性过滤（可选）：
      "applicableTerminalModes": ["HA","HH"],
      "excludedTerminalModes": ["HE"],
      "applicableBandwidths": ["SWB"],
      "applicableNetworks": ["VOLTE"],
      "applicableVocoders": ["EVS_SWB"],
      "applicableCustomers": ["MOTO"]
    }
  ]
}
```

## 4. 新增工作模式标准化流程

当需要引入新的工作模式（如VENICE Electrical Interface）时，按以下步骤操作：

### 4.1 探索阶段

1. **收集样本文件**: 获取新模式的测试报告（NB/WB/SWB各至少1份）+ checklist模板
2. **运行探索脚本**: 使用 `scripts/explore-venice-report.js`（可复用模板）解析报告
3. **分析输出**: 确认Detailed行的SMD/Name/Description/Direction/Unit命名体系
4. **分析checklist**: 解析目标工作表，映射outputCell与测试项对应关系

### 4.2 规则编写阶段

5. **创建规则文件**: 复制最接近的现有规则文件作为模板，逐项调整
6. **关键差异处理**:
   - 单位差异（如dBV(A) vs dBPa(A)）
   - 测试项命名差异（如SJLR vs SLR）
   - 独有测试项（如ECC特性分类）
   - 缺失测试项（如无sidetone）
7. **更新规则入口**: 在 `moto_rules_for_analysis.json5` 新增profile

### 4.3 代码适配阶段

8. **扩展模式识别** (`reportExtractor.js`):
   - `resolveTerminalModeFromInterface()`: 新增terminalMode识别
   - `resolveTerminalModeKey()`: 新增→profileKey映射
   - `resolveChecklistModeKeyFromName()`: 新增文件名关键词
   - `buildChecklistModeTokens()`: 新增匹配token
   - `resolveRuleProfileKey()`: 新增分支
   - `modeNameMap`: 新增checklist工作表名映射

9. **扩展自动推断** (`xlsxReportSource.js` / `reportSource.js`):
   - 文件名推断：新增关键词识别
   - Measurement Object推断：新增token候选
   - `normalizeTerminalMode()`: 新增分支

10. **扩展checklist匹配** (`reportExtractor.js`):
    - `findModeChecklistTemplate()`: 支持新模式关键词

### 4.4 验证阶段

11. **编写回归测试脚本**: 参考 `scripts/test-ei-extraction.js`
12. **运行测试**: 对NB/WB/SWB三份报告运行完整提取
13. **调优规则**: 根据命中率调整关键词/suffix配置
14. **回归验证**: 运行现有测试确保不破坏已有模式

## 6. 常见问题

### Q: 为什么有些测试项提取不到？
A: 按优先级排查：
1. 报告是否被正确解析（检查Detailed行数）
2. terminalMode是否被正确识别（检查reportContext）
3. coreKeywords是否覆盖报告中的实际文本（运行探索脚本对比）
4. suffix配置是否正确（MAX vs MAX-1区分）
5. 适用性过滤是否误排除（检查applicableBandwidths等）

### Q: 如何调优关键词？
A: 运行探索脚本输出报告中的所有SMD/Name组合，确保coreKeywords的关键词都在这些文本中出现。注意归一化后的匹配（大小写、空格、序号都会被处理）。

### Q: 新增模式需要改多少代码？
A: 最少需要改4个文件：规则入口(1行)、reportExtractor.js(6处函数)、xlsxReportSource.js(1处)、reportSource.js(1处)。如果自动推断不需要，甚至可以只改前2个。
